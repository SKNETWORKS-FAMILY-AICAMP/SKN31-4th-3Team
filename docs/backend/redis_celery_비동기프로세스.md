# 비동기 작업에서 Redis와 Celery의 이용 목적과 목표

웹 애플리케이션이나 백엔드 시스템에서 **Celery**와 **Redis**는 오래 걸리거나 비동기로 처리해야 하는 작업을 효율적으로 분리하여 실행하기 위해 함께 사용됩니다. 

두 기술의 역할, 도입 목적, 그리고 최종 목표를 체계적으로 정리합니다.

---

## 1. 각 기술의 핵심 역할

웹 서버(Django, Flask, FastAPI 등)가 사용자의 요청을 처리할 때 시간이 오래 걸리는 작업이 포함되어 있으면 응답이 지연됩니다. 이를 해결하기 위해 작업을 백그라운드로 넘겨 처리하는데, 이때 사용되는 구조가 **Producer-Broker-Worker** 구조입니다.

* **Celery (분산 작업 큐 관리 프레임워크)**
  * **Worker (일꾼):** 전달받은 작업을 백그라운드에서 실제 실행하는 프로세스입니다.
  * **Scheduler (Celery Beat):** 정해진 시간이나 주기마다 실행되어야 하는 정기 작업(Cron job)을 관리합니다.
  * **Task Management:** 실패한 작업의 재시도(Retry), 우선순위 부여, 작업 병렬 처리 등을 총괄합니다.

* **Redis (메시지 브로커 & 결과 저장소)**
  * **Message Broker (우체통):** 웹 서버가 생성한 "할 일(Task)"을 안전하게 보관하다가 Celery Worker에게 전달하는 중간 매개체입니다.
  * **Result Backend:** Celery가 작업을 수행하고 낸 최종 결과나 진행 상태를 저장하는 메모리 기반 데이터베이스 역할을 합니다.

---

## 2. 사용 목적 (Why to use)

### ① 응답 시간 최소화 (사용자 경험 개선)
회원가입 시 이메일 발송, 결제 후 영수증 PDF 생성, 이미지 업로드 후 썸네일 리사이징 등은 몇 초 이상 걸리는 작업입니다.
* **동기 방식:** 이메일 발송이 끝날 때까지 웹 화면이 로딩 상태로 멈춰 있음.
* **Celery + Redis 비동기 방식:** "이메일 발송 작업을 큐(Redis)에 담아라"라는 요청만 보낸 뒤, **사용자에게 즉시 "회원가입 완료" 응답**을 제공. 실제 발송은 백그라운드에서 Celery가 진행.

### ② 시스템 안정성 및 장애 격리 (Fault Tolerance)
서버에 갑자기 많은 요청이 몰리거나 외부 API(예: 결제대행사 서버)가 다운되더라도, 웹 서버 자체가 함께 다운되는 현상을 막습니다.
* 작업이 실패하더라도 웹 요청 전체가 실패하지 않고, Celery의 **재시도 정책(Retry Policy)** 을 통해 안정적으로 재처리할 수 있습니다.

### ③ 유연한 스케일링 (수평 확장성)
웹 서버의 부하와 백그라운드 작업 부하는 다릅니다.
* 웹 서버 인스턴스와 백그라운드 작업을 수행하는 Celery Worker 인스턴스를 **독립적으로 분리하여 확장**할 수 있습니다. (예: 대용량 비디오 처리가 몰리면 Celery Worker 서버만 추가 배치)

### ④ 주기적인 스케줄 작업 처리
매일 밤 12시 데이터베이스 백업, 매시간 통계 데이터 집계 등 정기적으로 실행해야 하는 스케줄링 작업을 Celery Beat를 통해 서버 로직과 깔끔하게 분리할 수 있습니다.

## 3. 도입의 궁극적 목표 (Goals)

| 목표 항목 | 설명 |
| :--- | :--- |
| **Non-blocking Architecture** | 웹 애플리케이션의 I/O 블로킹 현상을 제거하여 **서버의 요청 처리 능력(Throughput) 최적화** |
| **System Decoupling** | 핵심 웹 서비스 로직과 무거운 비즈니스 로직(알림, 데이터 분석 등)을 분리하여 **코드 유지보수성 증대** |
| **Reliability Guarantee** | 서버 장애 시에도 작업 데이터가 유실되지 않도록 보장하고, **실패한 작업에 대한 예측 가능한 복구** 환경 구축 |
| **Resource Efficiency** | CPU 및 메모리 집약적인 작업을 별도 전용 서버로 격리하여 **인프라 비용 및 효율성 최적화** |

## 4. 실제 동작 흐름 예시 (챗봇 대화 처리)

1. **Client → Web Server:** 사용자가 챗봇에 메시지(질문)를 입력하고 전송합니다.
2. **Web Server → Redis:** 웹 서버는 요청을 수신하고, Celery에게 `generate_chatbot_response.delay(chat_id, user_message)` 명령을 내려 백그라운드 생성 작업을 큐에 추가합니다.
3. **Redis (Message Broker):** 해당 챗봇 답변 생성 작업(Task)을 작업 큐(Queue)에 안전하게 보관합니다.
4. **Web Server → Client:** 웹 서버는 LLM/AI 연산 결과를 기다리지 않고, **`task_id`와 함께 "답변 생성 중..." 상태**를 클라이언트에 즉시 응답하여 연결이 끊기지 않도록 합니다.
5. **Redis → Celery Worker:** 한가한 Celery Worker가 Redis 큐에서 작업 메시지를 가져와 외부 LLM API 호출, RAG 데이터 검색, 답변 생성 등의 무거운 로직을 수행합니다.
6. **Celery Worker → Redis (Result Backend) & Client:** Celery Worker가 최종 생성된 챗봇 답변을 Redis(Result Backend) 또는 DB에 저장하고, WebSocket/SSE/폴링(Polling) 방식을 통해 클라이언트에 최종 답변을 전달합니다.
