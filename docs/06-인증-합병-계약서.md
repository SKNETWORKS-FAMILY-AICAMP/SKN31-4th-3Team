# Eden — 인증 합병 계약서

작성 시점: 2026-08-04
용도: 팀에서 만든 Django 로그인/로그아웃/회원정보 코드를 합칠 때의 기준

---

## 0. 결론부터

**지금 저장소의 `server/users/` 가 이미 프론트와 맞춰져 있습니다.** 팀 코드를 받으면
새로 붙이는 것이 아니라 **차이를 대조**하면 됩니다. 아래는 그 대조표입니다.

프론트에서 인증에 닿는 파일은 **딱 세 개**입니다.

| 파일 | 역할 |
|---|---|
| `frontend/src/services/apiClient.ts` | 토큰 보관, 자동 갱신, 401 처리 |
| `frontend/src/state/AuthContext.tsx` | "지금 누구인가" |
| `frontend/src/components/common/AccountButton.tsx` | 오른쪽 위 로그인/로그아웃 |

서버가 아래 계약만 지키면 이 세 파일은 **한 줄도 고칠 필요가 없습니다.**

---

## 1. 엔드포인트 계약

베이스 경로: `/api/v1/auth/`

### ① 회원가입 — `POST register/`

```jsonc
// 요청
{ "email": "a@b.com", "username": "혁진", "password": "8자이상", "mbti": "INFJ" }

// 201
{ "id": 1, "email": "a@b.com", "username": "혁진", "mbti": "INFJ" }
```

- `username` 은 **표시용 이름**입니다. 로그인 ID 가 아닙니다.
- `mbti` 는 서버에서 **선택**(`blank=True`)이지만 **프론트가 필수로 막습니다.**
  비워 두면 오른쪽 목록에서 아무것도 빛나지 않아 사용자가 고장으로 읽기 때문입니다.
  → **서버 쪽을 required 로 바꾸지 마세요.** 나중에 "나중에 고를게요"를 허용할 여지를 남깁니다.

### ② 로그인 — `POST login/`

```jsonc
// 요청 — USERNAME_FIELD 가 email 이므로 username 이 아니라 email 이다
{ "email": "a@b.com", "password": "..." }

// 200
{ "access": "...", "refresh": "..." }
```

> ⚠️ **가장 흔한 합병 사고**: SimpleJWT 기본 설정은 `username` 을 받습니다.
> `USERNAME_FIELD = "email"` 이 빠지면 로그인만 조용히 400 을 냅니다.

### ③ 토큰 갱신 — `POST refresh/`

```jsonc
{ "refresh": "..." }   →   { "access": "..." }
```

`ROTATE_REFRESH_TOKENS` 를 켜면 응답에 새 `refresh` 가 함께 옵니다.
`apiClient.ts` 는 **둘 다 처리합니다** — 오면 갱신하고, 없으면 기존 것을 유지합니다.

### ④ 내 정보 — `GET / PATCH me/` (인증 필요)

```jsonc
// GET 200
{ "id": 1, "email": "a@b.com", "username": "혁진", "mbti": "INFJ" }

// PATCH — 화면 오른쪽에서 유형을 고르면 여기로 남는다
{ "mbti": "ENFP" }   →   { "mbti": "ENFP" }
```

`GET me/` 응답에 **`username` 과 `mbti` 가 반드시 있어야 합니다.**
빠지면 홈의 이름 인사와 오른쪽 목록의 발광이 동시에 사라집니다.

## 2. 로그아웃 — 지금은 서버에 없습니다

프론트는 **토큰을 버리는 것**으로 로그아웃합니다. 서버 호출이 없습니다.

이 상태에서도 안전한 이유는 access 토큰 수명이 짧기 때문입니다.
다만 refresh 토큰은 만료 전까지 살아 있으므로, 공용 PC 를 고려한다면 서버 쪽 무효화가 필요합니다.

### 팀 코드에 로그아웃이 있다면

`POST logout/` 로 refresh 토큰을 블랙리스트에 넣는 방식이 표준입니다.

```python
# settings.py
INSTALLED_APPS += ["rest_framework_simplejwt.token_blacklist"]
```

그렇게 되면 프론트에서 고칠 곳은 **`AuthContext.tsx` 의 `logout()` 하나**입니다.
지금 구조상 다른 파일은 건드리지 않습니다.

## 3. 상태 코드 계약

| 상황 | 코드 | 프론트 동작 |
|---|---|---|
| 로그인 실패 | 401 | 폼 아래에 오류 문구 |
| access 만료 | 401 | **자동으로 refresh 후 원 요청 재시도** |
| refresh 까지 만료 | 401 | `SESSION_EXPIRED` 이벤트 → 로그아웃 상태로 |
| 남의 자원 접근 | 403 또는 404 | 오류 화면 |
| 유효성 실패 | 400 | 필드 오류를 그대로 표시 |

**400 응답의 모양**이 중요합니다. DRF 기본 형태를 유지해 주세요.

```jsonc
{ "email": ["이미 사용 중인 이메일입니다."] }
```

`apiClient.ts` 가 이 모양을 읽어 한국어 문구를 만듭니다. 형태가 바뀌면
사용자에게 "요청을 처리하지 못했습니다" 만 보입니다 — 무엇이 잘못됐는지 알 수 없게 됩니다.

## 4. 합칠 때 대조할 것 — 체크리스트

받은 코드를 열면 이 순서로 보시면 됩니다.

- [ ] `User.USERNAME_FIELD == "email"` — 아니면 로그인이 조용히 깨집니다
- [ ] `User.mbti` 필드 존재, `max_length=4`, `blank=True`
- [ ] `username` 이 표시용 이름으로 쓰이는가 (로그인 ID 로 쓰고 있지 않은가)
- [ ] `GET me/` 응답에 `username`, `mbti` 포함
- [ ] `PATCH me/` 로 `mbti` 만 수정 가능
- [ ] URL 경로가 `/api/v1/auth/` 아래
- [ ] `SIMPLE_JWT` 의 access 수명 — 너무 길면 로그아웃이 무의미해집니다
- [ ] CORS 에 프론트 오리진 포함
- [ ] 마이그레이션 파일이 함께 왔는가

**충돌이 나면 서버 쪽 이름을 프론트에 맞추는 편이 쌉니다.** 프론트에서 고치려면
`httpRepositories.ts` 의 변환 계층까지 함께 손봐야 합니다.

## 5. 지금 확인할 수 있는 것

백엔드 없이도 가입·로그인 흐름이 화면에서 끝까지 돕니다.

```bash
cd frontend && npm run dev     # VITE_API_BASE_URL 없음 → 로컬 세션
```

이 로컬 세션은 **`VITE_API_BASE_URL` 이 생기는 순간 완전히 꺼집니다.**
`AuthContext.tsx` 안의 `if (!USING_API)` 분기가 전부이고, 서버가 붙으면
그 분기는 한 번도 실행되지 않습니다. 비밀번호는 저장하지도 검증하지도 않습니다.

붙일 때는 이것만 하면 됩니다.

```bash
echo "VITE_API_BASE_URL=http://localhost:8000" > frontend/.env.local
```

## 6. 이번 변경으로 달라진 것

| | 전 | 후 |
|---|---|---|
| 로그인 진입점 | 환경설정 안 | **오른쪽 위 상주** |
| 로그아웃 | 환경설정 안, 즉시 실행 | 오른쪽 위, **한 번 더 확인** |
| 가입 시 MBTI | 선택 (`select`) | **필수, 16칸 그리드** |
| 첫 방문 안내 | 없음 | **가입부터 시작하는 튜토리얼** |

계정을 오른쪽 위로 올린 이유는, 로그인 여부가 설정 항목이 아니라
**"지금 내 상태"** 이기 때문입니다. 메뉴를 열어야만 알 수 있으면
로그인한 줄 알고 쓰다가 대화를 잃습니다.
