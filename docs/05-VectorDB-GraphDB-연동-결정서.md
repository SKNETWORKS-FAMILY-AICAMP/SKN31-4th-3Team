# Eden — VectorDB · GraphDB 연동 결정서

작성 시점: 2026-08-04
대상: 성경전서 벡터 검색 + Neo4j Aura 지식 그래프 도입

---

## 0. 세 줄 요약

1. **성경전서는 이미 저장소에 있습니다.** `data/bible_structured.json` — 31,077절, `{book, chapter, verse, content}`. 새로 구할 것이 없습니다.
2. **VectorDB 는 이미 쓰기로 한 RDS PostgreSQL 에 pgvector 확장으로 얹습니다.** 새 서비스 없음, 추가 비용 $0.
3. **GraphDB 는 Neo4j Aura Free 로 충분합니다.** 노드 예산의 16% 만 씁니다.

**AWS 에 새로 만들 리소스는 없습니다.** 지금 `docs/02-AWS-배포-운영서.md` 의 구성 그대로입니다.

## 1. "AWS 에 DB 올리기" 를 어떻게 해석했는가

"AWS docs" 로 들으셨던 것은 셋 중 하나였을 가능성이 높습니다. 셋 다 검토했습니다.

| 후보 | 월 비용 | 판단 |
|---|---:|---|
| **OpenSearch Serverless (Classic)** | **$175 ~ $350** | ✗ 최소 OCU 과금이 있어, 검색을 한 번도 안 해도 이 금액이 나갑니다 |
| OpenSearch Serverless (NextGen) | 사용량 기반 | △ 2026-05 GA. scale-to-zero 지원. 검토 가치는 있으나 신규 기능이고 지금 규모엔 과잉 |
| Amazon DocumentDB | RDS 와 별도 인스턴스 | ✗ VPC 내부 전용 → 로컬 개발 시 터널링 필요. Mongo 문법을 새로 익혀야 함 |
| **pgvector on 기존 RDS** | **$0 추가** | ✓ **채택** |

### 왜 OpenSearch 를 접었나

발표 자료에 적힌 **전체 인프라 예상 비용이 월 $40** 입니다. OpenSearch Serverless 최소 구성만 얹어도 **$175 부터** 시작합니다 — 서비스 전체보다 검색 인덱스 하나가 4배 이상 비쌉니다.

그리고 그 돈을 낼 이유가 없습니다. OpenSearch 는 수백만~수억 건에서 빛나는 도구입니다. **우리 코퍼스는 31,077건**입니다. 이 크기에서는 근사 최근접(ANN) 인덱스조차 필요 없고, 전수 비교로도 수십 밀리초에 끝납니다.

> 코퍼스가 10배 이상 커지거나(주석·설교문 추가) 다국어 번역본을 여럿 싣게 되면 그때 OpenSearch NextGen 으로 옮깁니다. 그 이전에 옮기는 것은 비용만 늘고 검색 품질은 그대로입니다.

### 왜 pgvector 인가

- **RDS PostgreSQL 은 이미 아키텍처에 있습니다.** `CREATE EXTENSION vector;` 한 줄이면 끝입니다.
- 구절 메타데이터(book/chapter/verse)와 벡터가 **같은 테이블**에 있어, 필터링이 그냥 `WHERE` 절입니다. 별도 저장소면 "먼저 필터하고 → 그 id 로 벡터 검색" 같은 왕복이 생깁니다.
- Django ORM 안에서 다룹니다. 트랜잭션, 마이그레이션, 백업이 전부 기존 절차 그대로입니다.
- 31,077 × 768차원 float32 ≈ **95MB**. db.t4g.micro 로 여유롭습니다.

## 2. Neo4j Aura Free 로 되는가 — 계산

Aura Free 한도: **노드 200,000 / 관계 400,000**

### 노드 예산

| 라벨 | 개수 | 근거 |
|---|---:|---|
| `:Verse` | 31,077 | 성경 전체 |
| `:Book` | 66 | |
| `:Galaxy` | 13 | 그리스도 + 12제자 |
| `:Person` | ~300 | 주요 인물 |
| `:Theme` | ~120 | 기존 `themes` 필드에서 추출 |
| **합계** | **~31,600** | **한도의 16%** ✓ |

### 관계 예산 — 여기가 유일한 위험 지점

| 관계 | 개수 | |
|---|---:|---|
| `(:Verse)-[:IN_BOOK]->(:Book)` | 31,077 | |
| `(:Verse)-[:NEXT]->(:Verse)` | 31,011 | 문맥 확장용 |
| `(:Verse)-[:HAS_THEME]->(:Theme)` | ~90,000 | 절당 평균 3개 |
| `(:Verse)-[:MENTIONS]->(:Person)` | ~40,000 | |
| `(:Galaxy)-[:CURATES]->(:Verse)` | 702 | 현재 큐레이션 |
| **소계** | **~193,000** | 한도의 48% |
| ~~상호참조 전체 (TSK 등)~~ | ~~340,000~~ | **✗ 넣으면 한도 초과** |

**결론: 상호참조는 전량 적재하지 않고, 신뢰도 상위만 추립니다.** 절당 최대 5개로 자르면 ~150,000 개가 되어 총합 343,000 — 한도 안에 들어옵니다. 이 상한은 코드에 상수로 둡니다(`MAX_XREF_PER_VERSE`).

> 한도를 넘기면 Aura Professional(월 ~$65)로 올라가야 합니다. 상한을 두는 이유가 이것입니다.

## 3. 저작권 — 반드시 짚고 갈 것

`data/bible_structured.json` 의 본문이 **어느 번역본인지 확인이 필요합니다.**

- 한국어 성경 번역본 대부분은 **대한성서공회가 저작권을 보유**합니다. 개역개정판(1998)은 명확히 보호 대상입니다.
- 지금 프론트의 연관 구절 662개에 본문을 넣지 않고 **출처 + 자체 요약만** 둔 것이 이 이유였습니다.

### 이번 도입으로 달라지는 점

벡터 검색은 **본문 전체를 DB 에 저장**해야 성립합니다. 즉 지금까지 피해 온 지점을 정면으로 통과합니다.

**권장 처리 — 저장과 노출을 분리합니다.**

| | 정책 |
|---|---|
| DB 저장 | 전문 저장 (검색 인덱싱 목적) |
| 화면 노출 | **큐레이션된 702절만** 전문 표시 |
| 그 외 검색 결과 | 장·절 출처 + LLM 자체 요약 (지금 brief 티어와 동일) |

이러면 지금 프론트의 2단 구조가 그대로 유지되면서 검색 품질만 올라갑니다.

**실서비스 전에 확인할 것:** 번역본 출처, 그리고 대한성서공회의 비상업적/교육 목적 이용 허락 절차. 학내 프로젝트 발표 범위라면 대개 문제가 없지만, **공개 배포 시점에는 확인이 필요합니다.** 문서에 남겨 둡니다.

## 4. 그래서 저에게 알려주셔야 할 것 — 4가지

> ⚠️ **자격증명은 채팅에 붙여넣지 마세요.** `server/.env` 에 직접 넣어 주시면 됩니다(이미 gitignore 됨). 저에게는 "넣었다" 만 알려주시면 됩니다. 형식은 `server/.env.example` 에 미리 적어 두겠습니다.

### ① Neo4j Aura 인스턴스 (필수)

[console.neo4j.io](https://console.neo4j.io) 에서 **Free 인스턴스** 하나 생성 → 생성 시 내려받는 `.txt` 의 값을 `server/.env` 에:

```
NEO4J_URI=neo4j+s://xxxxxxxx.databases.neo4j.io
NEO4J_USERNAME=neo4j
NEO4J_PASSWORD=...
```

**저에게 알려주실 것:** "만들었다" + 인스턴스 리전(예: `asia-northeast1`). 리전은 지연시간 계산에만 씁니다.

### ② 임베딩 모델 (필수)

한국어 성경이라 모델 선택이 검색 품질을 좌우합니다. 두 가지 안:

| | OpenAI `text-embedding-3-small` | 로컬 `ko-sroberta-multitask` |
|---|---|---|
| 차원 | 1536 | 768 |
| 최초 적재 비용 | **약 $0.03** (31,077절 1회) | $0 |
| 질의당 비용 | 사실상 0 | $0 |
| 서버 요구사항 | 없음 | **EC2 t3.small(2GB)엔 부담** |
| 한국어 품질 | 좋음 | 한국어 특화라 대등하거나 더 나음 |

**권장: OpenAI.** 3센트짜리 1회 비용으로 EC2 메모리 압박과 콜드스타트를 통째로 피합니다. LLM 붙일 때 어차피 키가 필요합니다.

**저에게 알려주실 것:** 둘 중 하나. OpenAI 면 `OPENAI_API_KEY` 를 `.env` 에.

### ③ 그래프에 무엇을 담을지 (선택 — 없으면 제가 만듭니다)

지금 저장소에 **상호참조·인물·주제 데이터가 없습니다.** 세 가지 방법이 있습니다:

- **(a) 있으면 주세요** — 팀이 만든 인물/사건/상호참조 CSV·JSON 이 있다면 그게 최선입니다.
- **(b) 공개 데이터** — Treasury of Scripture Knowledge(퍼블릭 도메인) 상호참조를 씁니다. 신뢰도 상위 5개만.
- **(c) LLM 추출** — 31,077절을 훑어 인물·주제를 뽑습니다. 1회 비용이 발생하고 검수가 필요합니다.

**권장: (b) 로 시작하고, 큐레이션된 702절만 (c) 로 보강.** 전체를 LLM 으로 돌리는 건 비용 대비 이득이 적습니다.

**저에게 알려주실 것:** (a) 에 해당하는 파일이 있는지 여부.

### ④ 확인만 해 주실 것

- `data/bible_structured.json` 이 **어느 번역본**인가 (3장 참조)
- RDS PostgreSQL **버전** — pgvector 는 15.2 이상 필요. 아직 안 만드셨으면 16 으로 생성해 주세요.

## 5. 없어도 지금 당장 할 수 있는 일

위 4가지가 하나도 없어도 **작업은 지금 시작합니다.** 원칙은 하나입니다:

> **자격증명이 없으면 기존 동작으로 조용히 폴백한다.**

- `NEO4J_URI` 없음 → 그래프 확장 건너뛰고 벡터 검색만
- 임베딩 키 없음 → 지금의 키워드 매칭(`match_intent`) 그대로
- 둘 다 없음 → **지금과 100% 동일하게 동작**

이렇게 두면 팀원 누구도 자격증명 없이 `git clone` 후 바로 돌릴 수 있고, 발표 당일 네트워크가 죽어도 데모가 살아 있습니다. 지금 `.env` 없이 mock 으로 도는 것과 같은 설계입니다.

## 6. 프론트에 반영되는 것 3가지 (요청하신 전부)

| # | 지금 | 연동 후 |
|:---:|---|---|
| ① | 별자리 선 = 프론트가 주제 유사도 + 거리로 계산한 MST | **Neo4j 의 실제 관계**를 간선으로 사용. 엣지 미제공 시 기존 MST 폴백 |
| ② | 추천 구절 카드에 근거 없음 | **"이 인물 · 이 주제를 거쳐 찾았습니다"** 경로 표시 |
| ③ | 상세 화면에 해당 구절 하나 | **"함께 보면 좋은 구절"** 2~3개 → 선택 시 그 별로 비행 |

**화면 코드는 거의 그대로입니다.** ①은 `constellation.ts` 가 계산하던 간선을 서버가 주는 간선으로 바꾸는 것이고, 렌더링·페이드·MBTI 필터는 전혀 건드리지 않습니다.

**좌표는 여전히 서버에 저장하지 않습니다.** 그래프가 들어와도 이 원칙은 유지합니다 — 서버의 책임은 `order` 와 `관계`까지, 화면 좌표는 프론트가 계산합니다.

## 7. 코드에서 붙는 자리

| 위치 | 지금 | 바뀔 것 |
|---|---|---|
| `server/scripture/intents.py::match_intent()` | 키워드 매칭 | 벡터 검색 + 그래프 확장 |

기존 `Verse` 모델과 702절 큐레이션은 **건드리지 않습니다.** 새 테이블을 옆에 두고 slug 로 연결합니다.
