## 1. 테스트 전략

### 1.1 무엇을 자동화하고 무엇을 안 하는가

| 대상 | 방식 | 이유 |
|---|---|---|
| 순수 로직 (검색 점수·좌표·주제 매칭) | 자동 | 값이 정해져 있다 |
| 컴포넌트 동작 (입력·키보드·상태 전이) | 자동 | 회귀가 잦다 |
| API 계약 (응답 필드·상태 코드) | 자동 | 프론트가 여기에 기댄다 |
| **실패 경로** (그래프 끊김·타임아웃·폴백) | 자동 | **가장 안 겪어 보는데 가장 조용히 깨진다** |
| 시각적 완성도 (별이 예쁜가) | 수동 | 못 잰다 |
| 외부 API 실제 호출 | **안 함** | 남의 네트워크 사정으로 빌드가 빨개진다 |

### 1.2 외부 의존을 테스트에 넣지 않는 원칙

Neo4j·OpenAI·Ollama 는 테스트에서 부르지 않는다. 대신 **반대쪽**을 못 박는다 —
그것들이 없거나 죽었을 때 화면이 도는가.

발표장에서 Aura 세션이 끊기는 쪽이 훨씬 그럴듯한 시나리오다.

### 관찰

**12건 중 6건을 사용자가 먼저 봤다.** 전부 "코드는 맞는데 결과가 조용히
비어 있는" 종류다 — 오류가 안 나고 화면도 멀쩡하다. 이런 것은 테스트로
잡히지 않는다. 그래서 D-03·D-04 이후 **배관 자체를 검사하는 테스트**
(`chat/test_context.py`)를 따로 만들었다.

외부 의존(Neo4j·Ollama·OpenAI)이 전부 죽어도 화면이 뜨고 구절을 볼 수 있다.
단일 실패점은 RDS 하나다.
