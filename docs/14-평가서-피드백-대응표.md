## 1. 코드 수정 후보 — 판단해 주세요

위험도는 **발표 전에 건드렸을 때 깨질 확률**입니다.

### 🔴 지금 판단할 가치가 있는 것

#### C-1. nginx SSE 버퍼링 (위험도 낮음 · 효과 큼)

**평가서**: "`proxy_buffering off;` 미흡 시 텍스트가 실시간 타이핑되지 않고
블록 단위로 묶여 출력"

**확인 결과**: 우리 `frontend/docker/nginx.conf` 에 **정말로 없습니다.**

```nginx
location /api/ { proxy_pass http://api:8000; include /etc/nginx/proxy_params_eden; }
```

`proxy_buffering` 기본값은 `on` 입니다. 지금 스트리밍이 되는 것처럼 보여도
nginx 가 조각을 모았다가 내보내고 있을 수 있습니다.

**고친다면** — `frontend/docker/proxy_params_eden` 에 세 줄 추가:

```nginx
proxy_buffering off;
proxy_cache off;
proxy_read_timeout 300s;
```

**위험**: nginx 설정 한 파일. 문법이 틀리면 컨테이너가 안 뜨는데, 그건
`deploy.sh` 의 헬스체크에서 바로 잡힙니다. 되돌리기도 한 줄입니다.

**판단 포인트**: 지금 발표에서 타이핑이 자연스럽게 보이면 굳이 안 건드려도
됩니다. 뚝뚝 끊겨 보이면 이게 원인입니다.

---

#### C-2. N+1 쿼리 (위험도 낮음 · 효과 작음)

**평가서**: "`prefetch_related` 미적용"

**우리 상태**: `VerseListView` 는 이미 `select_related("galaxy")` 를 씁니다.
`ChatSessionDetailView` 의 메시지 조회에는 없습니다.

**고친다면** — `chat/views.py`:

```python
def get_queryset(self):
    return ChatSession.objects.filter(user=self.request.user).prefetch_related("messages")
```

**위험**: 낮음. 다만 **대화 하나에 메시지가 수십 개 수준**이라 지금 규모에서
체감 차이가 없습니다. 발표에서 "N+1 을 알고 있고 이렇게 고칩니다" 라고
말하는 편이 실제 이득보다 큽니다.

---

#### C-3. 대화 생성 트랜잭션 (위험도 낮음 · 효과 작음)

**평가서**: "세션 생성과 첫 메시지 저장을 `@transaction.atomic` 으로"

**우리 상태**: 세션 생성과 첫 메시지가 **원래 분리된 요청**입니다
(`POST sessions/` → `POST completion/`). 한 트랜잭션으로 묶을 대상이 아닙니다.

**해당 없음.** 다만 `ChatCompletionView` 안에서 사용자 메시지 저장 →
LLM 호출 → 답변 저장이 이어지는데, 중간에 LLM 이 실패하면 사용자 메시지만
남습니다. 그건 **의도된 동작**입니다 — 사용자가 한 말은 지워지면 안 됩니다.

---

#### C-4. React.memo (위험도 중간 · 효과 작음)

**평가서**: "SSE 스트리밍 시 이전 메시지 재렌더링 방지"

**우리 상태**: 스트리밍 중 `CounselThread` 가 매 조각마다 다시 그립니다.
메시지가 20개쯤 되면 20개를 다시 그리는 셈입니다.

**고친다면** — 메시지 하나를 컴포넌트로 빼고 `React.memo`.

**위험**: 중간. 컴포넌트를 쪼개는 일이라 자동 스크롤·복사 버튼·안전 안내
분기가 함께 움직입니다. **테스트 761개가 지켜 주긴 하지만 발표 전에 할
일은 아닙니다.**

## 3. 발표에서 이렇게 답하면 됩니다

**"HTTPS 는 왜 안 했나요?"**
> 도메인이 없어 IP 로는 인증서를 발급할 수 없습니다. 도메인을 붙이는
> 시점에 Let's Encrypt 로 적용하는 것이 순서라고 봤습니다.

**"CI/CD 는요?"**
> `scripts/deploy.sh` 한 줄로 배포합니다. 무중단 배포가 필요한 규모가
> 아니고, 발표 전날 워크플로를 만들다 막히면 그 시간이 통째로 사라집니다.
> 트래픽이 생기면 그때 옮기는 것으로 판단했습니다.

**"비동기 예외 처리는요?"**
> 모든 요청에 타임아웃(15초)과 취소를 걸었고, 시간 초과와 사용자 취소를
> 구분해 다른 문구를 냅니다. 스트리밍만 타임아웃을 빼 두었는데, 긴 답변은
> 연결이 오래 열려 있는 것이 정상이기 때문입니다. 화면을 떠나면 진행 중인
> 스트림을 끊습니다.

**"N+1 은요?"**
> 구절 조회는 `select_related` 로 잡혀 있습니다. 대화 메시지 쪽은 대화 하나에
> 수십 건 규모라 지금은 체감 차이가 없어 두었고, 늘어나면
> `prefetch_related` 를 붙일 자리를 알고 있습니다.
