# Eden 통합 설계서 & API 계약서

React 프론트엔드와 Django 백엔드를 하나의 시스템으로 합친 결과를 정리합니다.

- 작성 기준: 합병 완료 시점
- 대상 저장소: `3RD_PROJECT/`
- 검증 상태: 백엔드 21개 · 프론트 373개 테스트 통과

---

## 1. 무엇을 합쳤는가

| | 합병 전 | 합병 후 |
|---|---|---|
| 프론트 | React + Vite, 전부 mock 데이터 | 같은 화면, 데이터는 Django 에서 |
| 백엔드 | ① FastAPI(구절·제자·MBTI·RAG) ② Django(인증·대화) 둘로 나뉨 | **Django 하나** |
| 인증 | 없음 | JWT (가입·로그인·갱신) |
| DB | 없음 | PostgreSQL (로컬은 SQLite 폴백) |

### 왜 Django 하나로 모았는가

서비스가 둘이면 배포 대상, 인증 경계, 장애 지점, AWS 비용이 전부 두 벌이 됩니다.
FastAPI 쪽에 있던 것은 도메인 데이터와 키워드 매칭이었고, 둘 다 Django 앱으로
옮기는 데 특별한 제약이 없었습니다. RAG(Vector DB)를 실제로 붙일 때가 되면
그때 다시 분리를 검토합니다 — 지금 나누면 얻는 것 없이 운영만 복잡해집니다.

## 2. 시스템 구성

```
브라우저
   │
   ├── 정적 파일 ──────→ S3 + CloudFront        (React 빌드 산출물)
   │
   └── /api/v1/* ──────→ EC2 : Nginx → Gunicorn → Django
                                              │
                                              └── RDS PostgreSQL
```

로컬에서는 Docker Compose 가 같은 경로 규칙을 재현합니다
(`/api` → Django, 나머지 → SPA). CORS·SPA 폴백 문제가 배포 후가 아니라
로컬에서 드러나게 하기 위해서입니다.

## 4. 데이터 흐름 — 시드는 프런트가 원본

구절 702개와 은하 13개는 프런트에서 저작했고, 이미 타입 검사와 테스트를
통과한 데이터입니다. 이것을 사람이 서버로 옮겨 적으면 반드시 어긋나고,
어긋나도 티가 나지 않습니다.

```
frontend/src/data/*.ts
        │  node server/scripts/export_seed.mjs
        ▼
server/scripture/fixtures/*.json
        │  python manage.py seed_scripture   (upsert, 여러 번 안전)
        ▼
      PostgreSQL
```

**좌표는 옮기지 않습니다.** 화면 좌표는 `galaxy/placement.ts` 가
"은하 안 순번(order)"에서 파생시킵니다. 서버가 좌표까지 들고 있으면
배치 규칙을 고칠 때마다 DB 를 다시 써야 하고, 두 규칙이 어긋나는 순간
별이 성운 밖에 뜹니다. 서버의 책임은 `order` 까지입니다.

## 5. API 계약

기준 URL: `{BASE}/api/v1`

### 5.1 인증 — `users`

| 기능 | Method | URL | 권한 |
|---|:---:|---|---|
| 회원가입 | POST | `/auth/register/` | 공개 |
| 로그인 | POST | `/auth/login/` | 공개 |
| 토큰 갱신 | POST | `/auth/refresh/` | 공개 |
| 내 정보 조회 | GET | `/auth/me/` | 로그인 |
| MBTI 변경 | PATCH | `/auth/me/` | 로그인 |

```jsonc
// POST /auth/register/
{ "email": "a@b.com", "username": "혁진", "password": "8자이상", "mbti": "INFJ" }  // mbti 선택
// → 201 { "id": 1, "email": "...", "username": "...", "mbti": "INFJ" }

// POST /auth/login/
{ "email": "a@b.com", "password": "..." }
// → 200 { "access": "...", "refresh": "..." }   Access 1일 / Refresh 7일
```

이후 요청은 `Authorization: Bearer <access>`.

### 5.2 말씀 — `scripture` (전부 공개)

읽기를 열어 둔 이유: 은하수를 둘러보고 구절을 읽는 것까지는 로그인 없이
되어야 합니다. 로그인은 "대화를 저장하고 이어가는" 시점에 필요합니다.

| 기능 | Method | URL |
|---|:---:|---|
| 은하 13개 | GET | `/scripture/galaxies/` |
| 구절 전체 | GET | `/scripture/verses/?galaxy=&depth=` |
| 구절 하나 | GET | `/scripture/verses/{slug}/` |
| 고민 → 추천 | POST | `/scripture/ask/` |

```jsonc
// GET /scripture/galaxies/  → 200 (페이지 없음)
[{ "id": "jesus", "name": "예수 그리스도", "role": "선한 목자",
   "mbti": "INFJ", "tint": "", "is_center": true, "order": 0 }, ...]

// GET /scripture/verses/    → 200, 702건 (페이지 없음)
[{ "id": "gen-1-3", "galaxy_id": "jesus", "order": 0,
   "book_code": "창", "book_name": "창세기", "chapter": 1, "verse": 3,
   "depth": "full",                    // "full" | "brief"
   "summary": "...", "themes": ["purpose","hope"], "motif": "light",
   "magnitude": 1.0,
   "excerpt": "빛이 있으라 ...",        // brief 는 "" (아래 5.4 참조)
   "attribution": "개역개정",
   "story": "...", "meditation": "...", "related_prompts": [...] }, ...]

// POST /scripture/ask/
{ "question": "요즘 너무 불안해요", "attempt": 0 }
// → 200
{ "question": "...", "intent": "anxiety",
  "empathy": "...", "reflection": "...",
  "verse_ids": ["php-4-6", "1pe-5-7", "mat-6-34"],
  "follow_ups": ["불안할 때 할 수 있는 게 있을까요?"] }
```

**`attempt` 의 의미** — "다른 구절 보기"를 누른 횟수입니다. variant 를
순환시킵니다. 난수를 쓰지 않는 이유는 같은 화면을 새로고침했을 때 결과가
달라지면 공유한 링크가 다른 내용을 보여 주기 때문입니다.

**`/verses/` 에 페이지를 두지 않은 이유** — 프론트는 첫 프레임에 전체 별을
그려야 합니다. 나눠 받으면 은하가 조각조각 나타납니다. 702건이고 정적인
데이터라 한 번에 줍니다(gzip 약 90KB).

### 5.3 상담 — `chat` (전부 로그인 필요)

| 기능 | Method | URL |
|---|:---:|---|
| 상담 시작 | POST | `/chat/threads/` |
| 대화방 목록·생성 | GET/POST | `/chat/sessions/` |
| 대화방 상세·삭제 | GET/DELETE | `/chat/sessions/{id}/` |
| 메시지 목록 | GET | `/chat/sessions/{id}/messages/` |
| 메시지 전송 | POST | `/chat/sessions/{id}/completion/` |

```jsonc
// POST /chat/threads/     — 세션 생성과 첫 안내를 한 번에
{ "verse_id": "gen-1-3" }          // 또는 { "question": "..." }, 또는 {}
// → 201
{ "thread_id": 12,
  "opening": { "id": 34, "role": "assistant",
               "content": "창세기 1:3에서 이어서 ...",
               "verse_id": "gen-1-3", "created_at": "..." } }

// POST /chat/sessions/12/completion/
{ "message": "요즘 외롭고 아무도 없는 것 같아요" }
// → 201 { "id": 35, "role": "assistant", "content": "...", "verse_id": "gen-1-3", ... }
```

`/threads/` 를 따로 둔 이유: 세션을 만들고 다시 첫 메시지를 받으면 화면이
두 번 깜빡입니다. 프런트의 `startThread` 계약도 한 번에 둘을 받습니다.

### 5.4 이름 규칙 변환

Django 는 `snake_case`, 화면은 `camelCase` 로 말합니다.
변환은 `httpRepositories.ts` 한 곳에서만 합니다.

| 서버 | 화면 |
|---|---|
| `verse_ids` | `verseIds` |
| `follow_ups` | `followUps` |
| `related_prompts` | `relatedPrompts` |
| `galaxy_id` | `discipleId` |
| `role: "assistant"` | `role: "guide"` |
| `order` | → `coord` (파생) |

## 6. 지켜야 하는 원칙

### 6.1 위기 판정은 클라이언트에 남는다

`services/intentMatcher.ts` 의 `isCrisis()` 를 서버로 옮기지 마세요.
서버가 죽거나 네트워크가 끊겨도 안전 안내는 떠야 합니다. 프론트는 요청
**이전에** 스스로 판정하고, 위기로 보이면 API 를 호출하지 않습니다.
서버(`scripture/intents.py`)의 판정은 그 위에 한 겹 더 두는 것이며,
대체가 아니라 추가입니다.

관련 테스트: `routes/AskRoute.test.tsx`, `routes/CounselRoute.test.tsx`

### 6.2 연관 구절 662개에는 본문 인용이 없다

번역본 저작권을 확인할 수 없는 인용을 662건 싣지 않기 위해, 장절과
자체 요약만 담았습니다. `Verse.excerpt`/`attribution` 이 비어 있는 것은
누락이 아니라 의도입니다.

**연동 시 가장 먼저 채워야 할 구멍**입니다. 정식 번역본 API 또는
라이선스를 확보하면 이 필드를 채우는 것만으로 두 층이 같은 화면을 씁니다.

관련 테스트: `data/verses.test.ts` — "연관 구절에는 본문 인용이 없다"

### 6.3 장절은 손으로 고치지 않는다

702개 장절은 저장소의 `data/bible_structured.json`(31,077절 전문)과
대조해 실재를 확인한 뒤 생성했습니다. 고쳐야 한다면 같은 대조를 다시
거치세요. 존재하지 않는 장절이 하나라도 섞이면 서비스 전체의 신뢰가
무너집니다.

### 6.4 남의 대화를 볼 수 없다

모든 대화 조회는 `request.user` 로 먼저 좁힌 뒤 진행합니다. id 만으로
접근하게 두면 번호를 바꿔 가며 남의 대화를 읽을 수 있습니다.

관련 테스트: `tests/test_integration.py::TestAuthWall::test_cannot_read_others_thread`

## 7. 아직 붙지 않은 것

| 항목 | 지금 | 붙일 자리 |
|---|---|---|
| **LLM** | `chat/guide.py` 의 `reply()` 가 템플릿으로 답함 | 그 함수 안쪽만 교체. 호출부는 그대로 |
| **RAG / Vector DB** | 키워드 매칭 (`scripture/intents.py`) | `match_intent()` 시그니처 유지하고 내부를 임베딩 검색으로 |
| **스트리밍(SSE)** | 완성된 답을 한 번에 반환 | `ChatCompletionView` → `StreamingHttpResponse` |
| **성경 본문** | 연관 구절은 요약만 | `Verse.excerpt` / `attribution` 채우기 |
| **Redis / Celery** | 미사용 (requirements 에서 주석 처리) | 스트리밍·비동기 작업 시 |

`llm_core/services.py` 에 OpenAI 호출 코드가 이미 있지만 아직 아무도
부르지 않습니다. 연동 시 `chat/guide.py` 의 `reply()` 에서 호출하면 됩니다.

## 8. 합병 중 발견해 고친 것

| 발견 | 조치 |
|---|---|
| `requirements.txt` 의 `Django==6.0.7` 이 존재하지 않는 버전 | `>=5.2,<6.0` (현재 LTS)로 수정. 그대로 두면 Docker 빌드가 첫 줄에서 멈춤 |
| `ALLOWED_HOSTS = []` 하드코딩 | 환경변수로 전환 (`ALLOWED_HOSTS`) |
| `SECRET_KEY` 가 없으면 즉시 크래시 | 개발 기본값 + `.env.example` 제공 |
| `DATABASE_URL` 필수 | 없으면 SQLite 폴백 — 첫 실행 장벽 제거 |
| `STATIC_ROOT` 미설정 | `collectstatic` 대상 지정 (Nginx 서빙) |
| Throttle 없음 | 익명 60/분, 로그인 120/분 |
| 헬스체크 없음 | `/healthz/` (DB 를 건드리지 않음) |
| `DEFAULT_AUTO_FIELD` 미설정 | 앱마다 경고가 뜨던 것 해소 |

## 9. 실행 방법

### 로컬 (백엔드 없이 화면만)

```bash
cd frontend && npm install && npm run dev     # → http://localhost:5173
```

`VITE_API_BASE_URL` 이 없으면 mock 으로 돕니다.

### 로컬 (전체)

```bash
docker compose up --build      # → http://localhost
```

### 서버만 직접

```bash
cd server
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env                 # SECRET_KEY 채우기
python manage.py migrate
python manage.py seed_scripture      # 은하 13 · 구절 702
python manage.py runserver           # → http://localhost:8000/api/v1/docs/
```

### 시드 다시 만들기 (프런트 데이터를 고친 뒤)

```bash
cd frontend && npx vite-node ../server/scripts/export_seed.mjs
cd ../server && python manage.py seed_scripture
```
