# 배포 체크리스트 — 발표 전날

위에서 아래로 그대로 따라 하면 됩니다. **각 단계의 확인 항목을 통과하지 못하면
다음으로 넘어가지 마세요.** 뒤에서 원인을 찾는 것이 훨씬 비쌉니다.

구성:

```
CloudFront/S3 (선택)      또는  EC2 의 nginx 가 프론트까지 서빙
        │
   EC2 g4dn.xlarge        Django + nginx + Ollama(GPU)
        │
   RDS db.t4g.micro       PostgreSQL 16 + pgvector
```

---

## 0. 시작 전 (5분)

- [ ] **Billing → Budgets → $15 알림** 설정
- [ ] Service Quotas → EC2 → `Running On-Demand G and VT instances` 가 4 이상
      (단위는 vCPU. g4dn.xlarge 는 4)

---

## 1. RDS 먼저 (20분, 대기 시간이 길다)

RDS 생성에 10~15분이 걸립니다. **EC2 보다 먼저 시작해 두면** 그 시간에
EC2 를 세팅할 수 있습니다.

- [ ] RDS → PostgreSQL 16 → **db.t4g.micro**, gp3 20GB
- [ ] DB 이름 `eden`, 사용자 `eden`, 비밀번호는 직접 생성
- [ ] **퍼블릭 액세스: 아니요**
- [ ] 보안 그룹: 새로 만들고 이름 `eden-db-sg`

> **비밀번호를 채팅·이슈·커밋에 붙이지 마세요.** EC2 에서 `.env.prod` 에
> 직접 입력합니다.

생성이 시작되면 바로 2번으로 넘어갑니다.

---

## 2. EC2 (30분)

- [ ] AMI: **Deep Learning** 검색 → Ubuntu 22.04 (NVIDIA 드라이버 포함)
- [ ] 인스턴스: **g4dn.xlarge**
- [ ] 스토리지: **gp3 100GB**
      (DLAMI 는 기본 이미지가 크다. 60GB 로 잡으면 모델 받다 꽉 찬다)
- [ ] 키페어 생성 → `.pem` 보관
- [ ] 보안 그룹 `eden-web-sg`
      - `22` ← **내 IP만**
      - `80` ← 0.0.0.0/0

**확인**
```bash
ssh -i eden.pem ubuntu@<EC2_IP>
nvidia-smi          # GPU 이름과 메모리가 보여야 한다
```

---

## 3. RDS 보안 그룹 연결 (2분)

- [ ] `eden-db-sg` 인바운드에 `5432` ← **`eden-web-sg`** 추가

> IP 가 아니라 **보안 그룹**으로 지정합니다. IP 로 열면 EC2 를 다시 만들
> 때마다 규칙을 고쳐야 합니다.

---

## 4. Ollama (20분, 대부분 다운로드)

```bash
git clone <레포주소> ~/4TH_PROJECT
cd ~/4TH_PROJECT
bash scripts/ec2-setup.sh
```

**확인 — 여기가 관문입니다**
- [ ] `✓ 임베딩 정상` 이 떴다
- [ ] `✓ GPU 사용 중` 이 떴다

> `⚠ CPU 로 돌고 있을 수 있습니다` 가 뜨면 질문 하나에 5~15초가 걸립니다.
> 발표에서 그 시간은 매우 깁니다. 여기서 멈추고 원인을 찾으세요.

**여기까지 되면 즉시 AMI 를 만드세요.** (인스턴스 → Actions → Image →
Create image) 이후에 뭘 망가뜨려도 돌아올 지점이 생깁니다.

## 5. 환경변수 (10분)

```bash
cp .env.prod.example .env.prod
nano .env.prod
```

- [ ] `SECRET_KEY` — `python3 -c "import secrets; print(secrets.token_urlsafe(64))"`
- [ ] `ALLOWED_HOSTS` 에 EC2 퍼블릭 IP
- [ ] `CSRF_TRUSTED_ORIGINS=http://<EC2_IP>`
- [ ] `DATABASE_URL` — RDS 엔드포인트
- [ ] `OLLAMA_HOST=http://host.docker.internal:11434` (기본값 그대로)

**확인**
```bash
psql "$DATABASE_URL" -c "SELECT 1"    # 안 되면 보안 그룹을 다시 보세요
```

---

## 6. pgvector 확장 (2분)

RDS 는 확장이 자동으로 켜지지 않습니다.

```bash
psql "$DATABASE_URL" -c "CREATE EXTENSION IF NOT EXISTS vector;"
```

- [ ] 오류 없이 실행됐다

> 이걸 빼먹으면 `migrate` 는 통과하고 **임베딩 컬럼만 조용히 안 생깁니다.**
> 그러면 검색이 폴백으로 떨어지고 화면은 멀쩡해 보입니다.

---

## 7. 배포 (10분)

```bash
bash scripts/deploy.sh
```

- [ ] `✓ API 응답`
- [ ] `검색 준비: True / 모델: oll8b`

`False` 가 나오면 임베딩이 아직 없는 것입니다. 8번으로 갑니다.

---

## 8. 데이터 적재 (40~90분 ← 가장 오래 걸림)

```bash
docker compose -f docker-compose.prod.yml --env-file .env.prod exec api \
  python manage.py ingest_bible

docker compose -f docker-compose.prod.yml --env-file .env.prod exec api \
  python manage.py ingest_bible --embed --model oll8b --resume

docker compose -f docker-compose.prod.yml --env-file .env.prod exec api \
  python manage.py assign_galaxies --by-embedding --canvas 150
```

> **시간이 없으면 로컬 DB 를 그대로 옮기는 편이 훨씬 빠릅니다.**
> ```bash
> # 로컬에서
> pg_dump -Fc eden > eden.dump
> scp -i eden.pem eden.dump ubuntu@<EC2_IP>:~
> # EC2 에서
> pg_restore -d "$DATABASE_URL" --no-owner eden.dump
> ```
> 87분 걸린 임베딩을 다시 돌리지 않아도 됩니다. **이쪽을 권합니다.**

## 9. 마지막 확인 (10분)

- [ ] `http://<EC2_IP>` 가 열린다
- [ ] 인트로 → 홈 → 질문 → 구절 카드가 뜬다
- [ ] 회원가입이 된다
- [ ] 상담 대화가 오간다
- [ ] 사이드바에 대화가 남는다
- [ ] **질문 응답이 2초 안에 온다** (느리면 Ollama 가 CPU 로 도는 것)

---

## 10. 발표 후 — 그날 안에

과금을 멈추려면 **중지가 아니라 삭제**여야 합니다. RDS 는 중지해도
7일 뒤 자동으로 다시 켜집니다.

- [ ] RDS 스냅샷 → RDS **삭제**
- [ ] EC2 **종료(terminate)**
- [ ] EBS 볼륨이 남아 있으면 삭제
- [ ] AMI·스냅샷 정리
- [ ] Elastic IP 를 할당했다면 **해제**

## 막혔을 때

| 증상 | 먼저 볼 곳 |
|---|---|
| 화면이 안 뜬다 | `docker compose -f docker-compose.prod.yml --env-file .env.prod logs web` |
| API 500 | `… logs api` |
| DB 연결 실패 | `eden-db-sg` 인바운드에 `eden-web-sg` 가 있는지 |
| 추천이 예전 구절만 | `pgvector` 확장 + `EmbeddingRun` 기록 확인 |
| 응답이 5초 이상 | `nvidia-smi` 에 ollama 가 보이는지 |
| 로그인이 안 풀림 | `ALLOWED_HOSTS` 에 EC2 IP 가 있는지 |
